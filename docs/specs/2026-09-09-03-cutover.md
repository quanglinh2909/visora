# Cutover: replacing gstreamer_c with Visora

**Date:** 2026-09-09
**Status:** ready to run
**Umbrella:** `docs/specs/2026-09-09-02-replacing-gstreamer-c.md`

## What "done" means

Visora replaces `gstreamer_c` when it does the same job on the same hardware
against the same data. Not when it compiles, and not when its own tests pass —
those are necessary and neither is the question.

Three things have to hold, and each is checkable rather than arguable:

1. **The three external contracts are unchanged.** They are already pinned by
   tests and verified against the real consumers:
   - the inference result socket — byte-compatible, and the actual
     `gstreamer_ai_python` consumer parses it (verified 2026-09-09, 60 messages,
     boxes and JPEG both correct);
   - the MoQ frame format — pinned byte by byte, verified against a consumer
     that decodes it the way the hub does;
   - the database schema — same tables and columns, so an existing deployment's
     data keeps working. `sql/schema.sql` is idempotent and safe on a populated
     database.

2. **The REST surface answers the same way.** 48 of the predecessor's 49
   endpoints exist; see below for the one that does not and why.

3. **It runs on the hardware the product ships on.** Every step has been
   verified on an RK3588 board as well as on x86_64, because a video system that
   only works on a workstation is not this product.

## The endpoint that is deliberately absent

`POST /ai-jobs/{id}/debug-arm` was a development aid: it faked an AI event to
test motion-triggered recording. Visora has `POST /cameras/{id}/ai-event`, which
does the same thing through the same gate and is a real feature rather than a
debug hook — an access-control reader or an alarm panel uses it. Adding a second
endpoint for the same action would be two ways to do one thing.

## Running both at once

They can run side by side on one machine against one database. Nothing in either
holds an exclusive lock on anything, and every port is configurable.

```bash
# gstreamer_c on its usual ports, unchanged.

# Visora beside it. Different HTTP and RTSP ports; the SAME database.
cat > /etc/visora/config.json <<'JSON'
{
  "server":    { "port": 8019 },
  "database":  { "url": "postgresql://user:pass@localhost/vms" },
  "gstreamer": { "rtspPort": 8654, "publicRtspHost": "192.168.1.10",
                 "recordingDir": "/var/lib/visora/recordings" },
  "ai":        { "modelDir": "/var/lib/visora/models", "analyseFps": 5 }
}
JSON
visora --config /etc/visora/config.json
```

Two things MUST differ while both run:

- **`recordingDir`.** Both write segments and both index them by path. Sharing a
  directory means each deletes the other's files at retention time.
- **the RTSP port**, obviously, and the AI result socket if both are to publish
  (`VISORA_RESULT_SOCKET`).

Sharing the `cameras` table is fine and is the point: both restream the same
cameras from the same configuration, so the comparison is like for like.

## What to compare

Run both for a working day against the same cameras, then check each of these.
They are ordered by how badly a difference would matter.

| # | Check | How |
|---|---|---|
| 1 | Every camera reaches `online` in both | `GET /camera-streams` on each, compare `state` per camera |
| 2 | Both restream continuously | `ffprobe` each output URL; no gaps in either |
| 3 | Recording covers the same wall-clock time | compare `recording_segments` ranges per camera; the totals should differ by less than one segment |
| 4 | Playback works from either index | `ffmpeg -i .../playback.m3u8 -f null -` against both |
| 5 | AI results agree | run the same job on the same camera in both, and compare detections on the same frames — see below |
| 6 | Motion fires on the same events | compare `motion_events` rows for a camera over the same window |
| 7 | CPU and memory | `pidstat` on both; Visora should not be worse, and on a board should be better where the shared source removed duplicate decodes |

### Comparing AI results properly

Do NOT compare detections frame by frame between the two running systems: they
analyse different frames, seconds apart, and any difference in the picture
becomes a difference in the output. That comparison always fails and never tells
you anything.

Compare on FIXED INPUT instead:

```bash
# The same picture, the same model, through each system's own inference path.
curl -s -X POST http://localhost:8019/inference/run \
  -H 'Content-Type: application/json' \
  -d "{\"image\": \"$(base64 -w0 sample.jpg)\", \"stages\": [
        {\"modelType\": \"yolov8_detect\",
         \"modelPath\": \"/var/lib/visora/models/yolov8n.rknn\",
         \"conf\": 0.4}]}"
```

Boxes should agree to within a pixel or two and classes exactly. A larger
difference means the letterbox, the dequantisation or the NMS differs, and each
of those is findable from the number.

## Rolling back

Visora writes to the same schema and adds no columns, so rolling back is
stopping it and starting `gstreamer_c` again. The recordings Visora wrote stay
readable by both: same container, same table, same paths.

The one thing that does not roll back is a camera created or edited through
Visora while it ran — it is simply a row, and `gstreamer_c` reads it fine.

## Retiring gstreamer_c

Once the comparison passes on the hardware in question:

1. Stop `gstreamer_c`.
2. Point Visora at the production `recordingDir`, or leave its own and let
   retention expire the old one.
3. Move `VISORA_RESULT_SOCKET` to `/tmp/ai_engine.sock` — the default, and what
   `gstreamer_ai_python` connects to.
4. Keep the `gstreamer_c` checkout. It is the reference for behaviour and for
   hardware detail nobody should have to rediscover; several comments in this
   repository point at measurements only recorded there.

## What is not finished

Honest list, so nobody discovers these during a cutover.

- **RF-DETR.** The one model type of the predecessor's that is not ported, and
  the reason is structural rather than effort: it is a HYBRID. Only its CNN
  backbone converts to an NPU graph; the transformer head has to run on ONNX
  Runtime, taking the backbone's FEATURE MAP as input. Every other type turns
  tensors into detections, which is what `vision::ModelType` is for; this one
  needs to run a second model on tensors, and `hal::Model::run` takes an image.
  Porting it means adding a tensors-in entry point to the inference port — a
  real addition to the HAL, not a new file — so it is deliberately left until
  someone needs it. Nothing else is blocked by it.

- **A camera deleted in Visora does not stop its AI jobs' rows.** The database
  cascades (`ON DELETE CASCADE` on `ai_jobs.camera_id`) and the runtime stops
  decoding for that camera, but the job list is only reloaded at startup, so a
  job for a deleted camera lingers in `GET /ai-jobs` until a restart. It runs
  nothing and harms nothing; it is untidy.

- **The face keypoint head of `yolov8_pose_face_in8.rknn` is coarse, and face
  alignment can only be as good as it is.** Its keypoint output is int8 with a
  scale of 3.67 model pixels per step — on a 1080p frame letterboxed to 640,
  that is about 11 SOURCE pixels of granularity. Faces on the board's cameras
  are 40 to 50 pixels tall, so eye-to-mouth spans barely two steps and the five
  landmarks can come back on a single row. Measured on the board, not inferred:
  the same face zoomed until it fills the input aligns cleanly and its embedding
  holds a cosine of 0.94 to 0.97 through 30 degrees of rotation, while the same
  face at its native 42 pixels gives landmarks that miss the eyes.

  Visora decodes those keypoints exactly as the predecessor did — same indexing,
  same letterbox unmapping — so this is not something the port introduced and
  not something to fix in this code. It is a limit on where face recognition can
  be expected to work: faces need to be large in frame, or the pose model needs
  re-exporting with a finer keypoint head.

- **Motion needs zones an operator actually drew, and the level is relative to
  the ZONE.** A zone covering the whole grid at level 1 needs a tenth of the
  WHOLE FRAME to move at once, which a person walking across it will not do.
  This is correct behaviour and it surprised the board verification: draw zones
  around what should trigger, not around everything.

## What was finished after the first cutover draft

Listed because the first draft named them as gaps and someone reading it will
otherwise plan around them.

- **The model types.** Pose, segmentation, PP-OCR detection, PP-OCR recognition
  and face embedding are ported, each as one file implementing
  `vision::ModelType`, decoding from tensors so they run on any backend. The
  predecessor's combined `paddle_ocr` type — one name that ran det and then rec
  — is deliberately NOT ported: a stage tree expresses the same thing without a
  special case, so it is two stages (`paddle_ocr_det` then `paddle_ocr_rec`) instead.

- **AI jobs are stored in PostgreSQL.** `store::PostgresAiJobRepository`, with
  the `ai_jobs` table in `sql/schema.sql`. The `stages` jsonb keeps the
  predecessor's exact shape — `inputClasses` and `classFilter` are
  comma-separated STRINGS, not arrays — so an existing deployment's jobs are
  read, and so a rollback to `gstreamer_c` can still read what Visora wrote.

- **Motion event snapshots.** `motion_events.image_path` is populated and
  `/motion-events/{id}/image` serves a real frame. The picture is copied off the
  decoder's thread on the rising edge of an event and encoded on a thread of its
  own, one per event rather than one per frame.

- **The RTSP restream uses the shared source.** Verified: three RTSP viewers,
  recording and motion detection on one camera, and exactly ONE connection to
  it. Still on demand — the source is acquired when a client first asks and
  released when the last one leaves.
